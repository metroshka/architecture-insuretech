# Событийная архитектура InsureTech

Для подключения десяти страховых компаний обновление продуктов и тарифов отделяется от запросов потребителей. `ins-product-aggregator` получает данные в фоне и публикует изменения в Kafka. `core-app` и `ins-comp-settlement` обновляют существующие локальные копии по событиям. Сведения об оформленных страховках также передаются событиями, поэтому ночной реестр строится из БД сервиса взаиморасчётов.

Решение показано в [диаграмме контейнеров](InsureTech_C4_event-driven_to-be.drawio): на первой странице — сервисы и связи, на второй — доставка событий и обработка сбоев.

## Вводные и ограничения

- Сейчас агрегатор в рамках одного синхронного запроса обращается к пяти страховым компаниям, объединяет ответы и возвращает список продуктов и тарифов. Планируется подключить ещё пять компаний.
- `core-app` запрашивает обновление раз в 15 минут, `ins-comp-settlement` — раз в сутки. Оба сервиса уже хранят локальные копии этих данных.
- `ins-comp-settlement` дополнительно получает из `core-app` все оформленные за день страховки одним ночным REST-запросом.
- Функциональная декомпозиция сохраняется: агрегатор интегрируется со страховыми по продуктам и тарифам, `core-app` оформляет страховки, `ins-comp-settlement` выполняет взаиморасчёты, `client-info` управляет клиентскими данными.
- Внешние API страховых сохраняются. Поддержка событий или webhook со стороны страховых не задана, поэтому используется фоновый опрос.
- Из Task1 сохраняется размещение приложений в Kubernetes и PostgreSQL в трёх зонах. Цилиндры БД на C4-схеме обозначают логические хранилища сервисов — отдельные схемы управляемого PostgreSQL с отдельными правами доступа.

## Проблемы и риски текущего решения

| Проблема или риск | Последствие при росте | Предлагаемое решение |
| --- | --- | --- |
| Обновление общего каталога связано с ответами всех страховых в одном запросе | Медленный API может задержать или сорвать обновление. При параллельном опросе время зависит от медленных ответов; последовательный опрос дополнительно суммирует задержки | Независимый фоновый опрос каждой компании и публикация её изменений без ожидания остальных |
| Каждый запрос потребителя запускает новый внешний опрос | При прежнем расписании переход с 5 на 10 компаний удвоит число обращений на одно обновление; повтор после ошибки дополнительно увеличит нагрузку | Один механизм опроса в агрегаторе; независимые подписки потребителей на полученные изменения |
| Нет изоляции медленных или неисправных интеграций в описанном сценарии | Занятые соединения, таймауты, лавина повторов и ограничения внешних API | Ограничение параллелизма, timeout, circuit breaker и rate limit отдельно по страховой; ограниченные retry с backoff и jitter |
| Потребители обновляют копии с разной периодичностью | До следующего успешного обновления используются прежние данные; после сбоя отставание может превысить обычные 15 минут или сутки | События после обнаружения изменений, версии данных, время последнего успешного опроса и контроль допустимой свежести |
| Ночная выгрузка страховок растёт вместе с продажами | Увеличиваются размер ответа, нагрузка на БД `core-app` и риск таймаута; повтор требует снова передавать большой объём | Поток оформленных страховок и накопление локальной копии в сервисе взаиморасчётов |
| Ночная обработка зависит от доступности `core-app` и агрегатора | Сбой в момент формирования реестра задерживает взаиморасчёты | Формирование реестра из собственной БД с проверкой полноты доставленных событий |
| Актуальный каталог и условия уже оформленной страховки могут различаться | Использование новой версии тарифа для старой страховки даст ошибочные расчёты | Сохранение суммы и снимка применённых условий при оформлении; передача этого снимка в событии |

Рост числа пользователей не означает, что каждый пользователь запускает опрос страховых: по условию обновление каталога выполняется по расписанию. Рост продаж прежде всего увеличивает поток страховок и объём ночного реестра. Рост числа страховых увеличивает объём внешнего опроса.

## Выбранные взаимодействия

| Взаимодействие | Изменение |
| --- | --- |
| `core-app` → агрегатор: периодическое получение каталога | Заменено чтением `catalog.products.v1` в consumer group `core-catalog` |
| `ins-comp-settlement` → агрегатор: суточное получение каталога | Заменено чтением того же topic в независимой группе `settlement` |
| `ins-comp-settlement` → `core-app`: ночная выгрузка страховок | Заменено чтением `policy.issued.v1` группой `settlement` |
| Агрегатор → страховые: получение продуктов и тарифов | Сохраняются существующие API, меняется запуск — фоновое расписание по каждой страховой |
| `ins-comp-settlement` → страховые: передача реестров | Сохраняются существующие API и ответственность сервиса |
| Web, партнёры, платежи и `client-info` | Существующие взаимодействия сохраняются; GraphQL для `client-info` относится к отдельному заданию |

Kafka выбрана как журнал событий с независимыми подписками и возможностью повторного чтения. Обеим службам нужна собственная копия каталога, поэтому они используют разные consumer groups. Экземпляры одного сервиса входят в его общую группу и делят обработку партиций. [Модель topics, partitions и повторного чтения Kafka](https://kafka.apache.org/intro/).

Альтернатива — предварительно собирать каталог в агрегаторе и оставить REST-опрос потребителей. Она проще, но сохраняет периодическое обновление копий и ночную выгрузку страховок. Для выбранных потоков событий Kafka позволяет потребителям восстанавливаться независимо и дочитывать накопленные изменения. Её цена — отдельная инфраструктура и сопровождение подписок.

## Обновление продуктов и тарифов

1. Агрегатор опрашивает каждую страховую независимо. Начальная проектная настройка — раз в 15 минут со сдвигом расписаний и ограничением одновременных запросов. Интервал уточняется по допустимому возрасту данных и лимитам API.
2. Полученный ответ проверяется и нормализуется. Изменение продукта сохраняется в собственном хранилище агрегатора вместе с новой `entityVersion` и событием в outbox в одной транзакции.
3. Фоновый publisher отправляет событие в `catalog.products.v1`. При неизменившихся данных событие изменения не создаётся; время успешного опроса обновляется отдельно.
4. Каждый потребитель применяет событие к своему каталогу. Это прикладные копии данных, а не физические реплики PostgreSQL.

Агрегатору добавляется отдельная схема `ins-product-aggregator-db`: нормализованный каталог, версии, outbox и состояние опроса. Планировщик и publisher входят в существующий сервис; новые бизнес-сервисы не выделяются. Для нескольких экземпляров используется lease на страховую с fencing-проверкой при сохранении результата: запоздавший ответ старого владельца не перезаписывает новый.

Ключ события — `insurerId + productId`. Полезная нагрузка содержит полное актуальное состояние продукта, тарифы, статус доступности и сроки действия. Удаление или деактивация передаются явно с новой версией. Если API возвращает полный список, отсутствие продукта считается удалением только после успешного получения и проверки всего списка, включая все страницы. Ошибка, таймаут или частичный ответ не являются признаком удаления.

При сбое страховой её последние данные сохраняются с отметкой времени. События не устраняют задержку обнаружения изменения во внешней системе. Для оформления нужно проверить срок действия тарифа и допустимый возраст данных; предельный возраст и поведение при его превышении согласуются с бизнесом.

## Передача страховок и формирование реестра

`core-app` создаёт `PolicyIssued` после успешного перехода страховки в состояние «оформлена». В одной транзакции сохраняются страховка, применённые условия и outbox. Создание заявки само по себе не считается оформлением страховки.

Ключ в `policy.issued.v1` — `policyId`. Событие содержит идентификаторы страховки, заявки и страховой, дату оформления, сумму, валюту, версию продукта и снимок условий, необходимых для взаиморасчётов. Паспортные данные в поток не включаются. Договорные расчёты используют сохранённые условия страховки, а не текущий тариф из каталога.

`ins-comp-settlement` сохраняет полученные сведения в собственной БД. Расписание формирования реестра остаётся суточным; массовый ночной REST-запрос к `core-app` исключается.

Для полноты реестра одного нулевого consumer lag недостаточно: часть событий может ещё находиться в outbox. В выбранном протоколе закрытия периода `core-app` фиксирует границу суток и завершение относящихся к периоду транзакций. После подтверждённой публикации всех событий периода publisher отправляет служебный маркер `AccountingPeriodClosed` в каждую партицию потока страховок. Маркер содержит период и идентификатор закрытия; он публикуется после событий соответствующего периода в этой партиции. Изменение числа партиций во время закрытия исключается.

Сервис взаиморасчётов завершает реестр после получения всех маркеров и устранения ошибок обработки за период. Если условие не выполнено, реестр остаётся незавершённым и формируется оповещение. Часовой пояс, граница суток и порядок учёта поздних оформлений согласуются с бизнесом. Поздняя запись закрытого периода должна попадать в согласованный корректирующий реестр, а не теряться. Сам протокол закрытия — проектное решение для сохранения полноты исходной суточной операции.

## Transactional Outbox и обработка повторов

Outbox используется в `core-app` и агрегаторе. Он связывает изменение данных и подготовку события одной локальной транзакцией, устраняя разрыв «данные сохранены, а уведомление потеряно». Publisher помечает запись отправленной только после подтверждения Kafka. При недоступности Kafka записи остаются в БД и отправляются после восстановления. [Паттерн Transactional Outbox](https://microservices.io/patterns/data/transactional-outbox.html).

Выбран polling publisher внутри каждого из двух сервисов: он читает outbox небольшими пакетами. Это не требует отдельного CDC-контура. Для одного ключа события отправляются по версии, следующая запись публикуется после подтверждения предыдущей. Координация владельца ключа между экземплярами и блокировки не допускают одновременную публикацию разных версий одного объекта. Простое конкурентное чтение произвольных строк outbox без сохранения порядка ключа не подходит.

Доставка имеет семантику **at-least-once**: событие может прийти повторно. Например, publisher может упасть после подтверждения Kafka, но до отметки в outbox. Повтор использует тот же `eventId`.

Потребитель в одной транзакции записывает `eventId` в inbox с уникальным ограничением и обновляет локальные данные. Известный `eventId` не вызывает повторного бизнес-эффекта. Offset Kafka подтверждается после COMMIT БД; подтверждается только непрерывная последовательность уже обработанных записей партиции. Если процесс упал между COMMIT и подтверждением offset, повтор безопасно отсекается inbox. [Семантика доставки и координация с внешним хранилищем](https://kafka.apache.org/41/design/design/#message-delivery-semantics).

Общий конверт события: `eventId`, `eventType`, `schemaVersion`, `entityVersion`, `occurredAt`, ключ объекта и полезная нагрузка. `schemaVersion` описывает формат сообщения, `entityVersion` — версию бизнес-объекта. Потребитель применяет полное состояние только при более новой версии. Kafka сохраняет порядок в пределах партиции; общего порядка между потоками каталога и страховок нет. Снимок условий в `PolicyIssued` позволяет выполнить расчёт независимо от очередности поступления каталога.

## Восстановление и эксплуатационные риски

| Ситуация | Поведение и контроль |
| --- | --- |
| Внешняя страховая недоступна | Изолированный timeout и ограниченные retry; старые данные сохраняются, возраст контролируется |
| Kafka недоступна | Publisher повторяет отправку; контролируются количество и возраст outbox, свободное место в PostgreSQL |
| Потребитель или его БД недоступны | Offset не подтверждается, обработка возобновляется после восстановления; контролируется lag |
| Событие нельзя обработать после ограниченных повторов | Исходное событие и причина сохраняются в карантин в БД потребителя до подтверждения offset; оповещение и контролируемый повтор с исходным eventId. Inbox успешной обработки не заполняется. Ошибка периода блокирует закрытие реестра |
| Потребитель отстал дольше срока хранения | Восстановление из согласованного снимка хранилища владельца и последующее чтение потока; одного старого offset недостаточно |
| Несколько экземпляров приложения | Общая consumer group внутри сервиса, независимые группы между сервисами; lease/fencing для опроса и сохранение порядка публикации одного ключа |
| Накопление inbox и outbox | Отправленные записи очищаются по политике хранения. Дедупликация хранится не меньше поддерживаемого окна повторов; версии и уникальный policyId дополнительно защищают восстановление |

Начальная загрузка выполняется до включения нового потребителя в рабочий процесс. Сначала фиксируются начальные offsets потока, затем выгружается согласованный снимок данных владельца, после чего дочитываются события с зафиксированных offsets. Снимок содержит версии и статусы объектов; повторное перекрытие устраняется версиями и идентификаторами. Записи Kafka должны сохраняться на всё время загрузки. Снимок предоставляется владельцем данных через служебную выгрузку; прямое чтение чужой схемы другим сервисом не вводится. После сверки количества и контрольных итогов выполняется переключение. Старый периодический обмен отключается, чтобы не осталось двух конкурирующих механизмов обновления.

Начальный retention обоих потоков — 7 дней, проектное допущение для восстановления после коротких остановок. Объём событий, дисковое место, срок хранения карантина и допустимый простой требуют оценки по реальной нагрузке. Для удаления старого карантинного события нужен отдельный разбор причины и восстановление пропущенного эффекта.

Проектная конфигурация Kafka согласуется с тремя зонами Task1: три брокера, распределение реплик партиций по зонам, `replication.factor=3`, `min.insync.replicas=2`, `acks=all`, `enable.idempotence=true`, запрет выбора несинхронизированной реплики лидером. Для KRaft обеспечивается кворум контроллеров в трёх зонах. При потере одной зоны публикация возможна при сохранении требуемых синхронных реплик и кворума; при их нехватке publisher сохраняет события в outbox. Эти настройки не заменяют проверку отказов и не дают общей транзакции Kafka с PostgreSQL. [Настройки репликации Kafka](https://kafka.apache.org/41/configuration/topic-configs/#min.insync.replicas).

Доступ к Kafka — по частной сети, с TLS, аутентификацией и ACL на нужные topics и группы. Основные метрики: свежесть опроса каждой страховой, задержка публикации из outbox, consumer lag, ошибки и возраст карантина, длительность и полнота формирования реестра. Рост outbox использует ресурсы общей БД, поэтому нужны лимиты, запас диска и оповещение до его исчерпания.

## Соответствие исходной диаграмме

Сохранены существующие бизнес-сервисы, клиент, Web, партнёры, платёжный сервис и страховые компании. Удалены три периодические REST-связи получения каталога и страховок, добавлены Kafka и логическое хранилище агрегатора. Планировщик, publisher и обработчики событий показаны как части существующих сервисов.

В исходном файле хранилище `client-info` ошибочно подписано `ins-comp-settlement-db`; в целевой схеме оно названо `client-info-db`, его назначение сохранено. Подпись общей границы «Виртуальная машина» заменена логической границей InsureTech, чтобы C4-схема не противоречила размещению из Task1.

Исходный материал: [диаграмма контейнеров InsureTech из задания](https://code.s3.yandex.net/software-architect/InsureTech_C4_%D1%81ontainer-diagram.drawio.xml).
